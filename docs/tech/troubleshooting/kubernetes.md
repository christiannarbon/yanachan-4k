# Troubleshooting: Kubernetes

```sh
make k8s-status    # pods, PVC, service, and whether the tunnel is alive
make k8s-logs      # follow the pod logs
```

`make k8s-status` also tells you when nothing is deployed at all.

## `make k8s-up` stops at the rollout

```sh
kubectl -n yana-chan-4k describe pod -l app.kubernetes.io/name=yana-chan-4k
```

**`ErrImageNeverPull` / `ImagePullBackOff`.** The image lives only in your local
cluster's node and `imagePullPolicy` is `IfNotPresent`. Load it:

```sh
make k8s-load
```

**Pending, unbound PVC.** The base PVC needs a default StorageClass. On minikube
that is `standard` and it is on by default; on a bare cluster you may not have
one.

**`CreateContainerConfigError`.** Usually the secret. Both keys are marked
optional, so this points at something else in the env block — check the describe
output.

## The pod runs but `/api/health` never answers

The container listens on `:19080`. If you changed `GHDASH_ADDR` in the
deployment, the probes and the service still point at 19080.

The health endpoint is deliberately exempt from the Host allowlist so probes can
address the pod by IP — a probe failing with a 403 means something else is in
front of it.

## The tunnel dies

```sh
make k8s-tunnel      # restarts it
make k8s-untunnel    # stops it
make k8s-open        # foreground instead, so you can see it fail
```

The background port-forward keeps its pid in `.k8s-portforward.pid` and its
output in `.k8s-portforward.log`, both at the repository root. `k8s-tunnel`
polls `/api/health` for 30 seconds and reports the log path if it never comes up.

A port-forward drops when the pod restarts. `make k8s-tunnel` after any
`k8s-restart`.

## The secret did not take

The pod reads the secret at startup, so a changed secret needs a restart:

```sh
make k8s-restart
```

To check what is actually in it:

```sh
kubectl -n yana-chan-4k get secret yana-chan-4k \
  -o jsonpath='{.data.gh-token}' | base64 -d | wc -c
```

Zero bytes means `make k8s-secret` ran without a token — either you answered `N`
at the prompt, or there was no terminal attached, which is treated as "no".
Set `GH_TOKEN` in the environment to skip the prompt:

```sh
GH_TOKEN=$(gh auth token) make k8s-secret k8s-restart
```

For the **prod** overlay the secret is deliberately not generated by kustomize —
create it out of band before applying.

## Changes to the manifests are not taking effect

```sh
make k8s-validate    # renders both overlays and schema-checks them
```

Then check you are on the overlay you think you are. Every `k8s-*` target
defaults to `OVERLAY=dev`:

```sh
make k8s-up OVERLAY=prod
```

## The rollout hangs on a second pod

The deployment is `strategy: Recreate` with one replica, on purpose: the state
directory is a ReadWriteOnce volume, so the old pod must release it before the
new one can start. If you changed the strategy to `RollingUpdate`, the new pod
will wait forever for a volume the old one still holds.

## `make k8s-down` deleted my session

That is what it does — it removes the PVC, and the session lives on it. Sign in
again next time. `make k8s-restart` is the non-destructive option when all you
want is a fresh pod.

The cluster itself survives `k8s-down`; only the app's namespace goes.

## The app 403s through the tunnel

The tunnel presents as `localhost`, which is on the allowlist, so this normally
cannot happen. If you reach the app under any other name — an Ingress, a proxy —
that name must be in `GHDASH_ALLOWED_HOSTS`. See
[networking](networking.md#403-unrecognised-host-header) and note the warning
there about authenticating proxies: the pod holds a GitHub token and has no
login of its own.
