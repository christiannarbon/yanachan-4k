# Internationalization

`frontend/src/i18n/`

Two languages, English and Japanese, with no i18n library. The mechanism is the
type system.

## Catalogs

```
i18n/en.ts       the source of truth, and the exported Messages type
i18n/ja.ts       typed as Messages
i18n/index.ts    locale state, and the derived helpers
i18n/Msg.vue     a sentence with inline markup
```

`en.ts` exports both the catalog and `type Messages` derived from it. `ja.ts` is
declared as `Messages`, so:

- A key added to English and not Japanese is a **compile error** in `ja.ts`.
- A key added to Japanese and not English is a **compile error** too.
- A string that should be a function — anything with a count or a date — cannot
  be a plain string in one language and a function in the other.

Strings are read as property access (`t.board.refresh`), never by key string, so
a typo is a type error rather than a blank on screen.

```sh
make test      # runs vue-tsc --noEmit, which is where all of this is enforced
```

## Two rules for writing copy

### Sentences with markup keep placeholders

A sentence that needs a `<code>` or a `<strong>` in the middle keeps a `{name}`
placeholder and renders through `Msg.vue`, which fills each placeholder from a
same-named slot:

```ts
teamsExplain: 'Each team becomes its own tab... Write them as {format}. ...'
```

```vue
<Msg :text="t.settings.teamsExplain">
  <template #format><code>org/team-slug</code></template>
</Msg>
```

That is what lets Japanese put the `<code>` where its own grammar wants it
rather than where English left it. Interpolating the markup into the string
would freeze English word order into every translation.

### Anything with a count or a date is a function

```ts
membershipsFailed: (warning: string) => `Could not list your memberships: ${warning}`,
```

Not a template with a hole in it. Each language does its own pluralising, its own
counter words, and its own ordering — a Japanese count often takes a counter
suffix that depends on what is being counted, and no interpolation scheme
survives that.

The date and number helpers live in `lib/time.ts` (`ago`, `stamp`, `day`,
`weekday`, `num`, `actorList`) and are called from the catalog, so formatting is
per-locale too.

## Locale state

`i18n/index.ts` is a module-level ref plus `localStorage` under `yana.locale`.
First visit runs `detectLocale()`, which walks `navigator.languages` and takes
the first supported base tag — `ja-JP` matches `ja`. Failing that, English.

Every `localStorage` access is wrapped in `try/catch`: private windows and
blocked site data throw rather than returning null.

## What the backend contributes

Section titles and the window label are worded **in the frontend**. The backend
sends a machine-readable `kind` alongside its own English `label`, and
`useI18n()` exposes `sectionTitle(section)` and `windowLabel(window)` which build
the sentence per locale. A client that does not translate can still print
`label`.

If you add a section kind or a window kind, add it to those two helpers. `Kind`
is a plain string on the wire, so this is one of the few places the type system
will not catch the omission.

## What is not translated

Errors relayed from the backend or from GitHub arrive in English in both
languages. A GraphQL error is GitHub's own text; paraphrasing it into Japanese
would mean translating an error message, which is worse than reading it as sent.
